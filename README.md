# MLA Appointment Management Website

A full-stack web app for booking and managing appointments with an MLA's office.

- **Citizens** submit a request (name, mobile, purpose, preferred date/time) and get a
  token number. They can look up their request status any time using their mobile number.
- **Admin dashboard** (MLA / assistant) sees every request in a List or Calendar view,
  and can **Approve**, **Reject**, or **Reschedule** each one. Citizens see the result
  the next time they check their status.

## Tech stack

- **Backend:** Node.js + Express
- **Storage:** Supabase (Postgres). `db/database.js` is the only file that talks to the
  database — every route in `server.js` just calls its exported functions, so the rest
  of the app doesn't know or care where data lives.
  - A JSON-file version is still included at `db/database.jsonfile.js` (no Supabase
    account needed) if you want to run it without any external setup — just rename it
    to `db/database.js` to switch back.
- **Frontend:** plain HTML/CSS/JS, no build step, no framework — open it and it runs.

## Supabase setup

1. Create a project at [supabase.com](https://supabase.com) (or use one you already have).
2. Go to **SQL Editor** → paste the entire contents of `supabase/schema.sql` → **Run**.
   This creates the `appointments` table, the `security_logs` table, the auto token-number generator,
   and the helper triggers for `created_at`/`updated_at`.
3. Optionally verify the schema by running:
   ```sql
   select * from information_schema.tables where table_schema = 'public' and table_name in ('appointments', 'security_logs');
   ```
4. Go to **Authentication → Users → Add user** if you later want to switch the admin
   login from the simple password gate to full Supabase Auth.
4. Go to **Project Settings → API Keys** and copy:
   - **Project URL**
   - **Secret key** (`sb_secret_...`) — server-only. Never expose this in the browser,
     commit it to a repo, or paste it anywhere public — including chat. If a secret key
     is ever exposed like that, rotate/regenerate it immediately from that same page.
5. Copy `.env.example` to `.env` and fill in the real values:
   ```bash
   cp .env.example .env
   ```
   ```
   SUPABASE_URL=https://your-project-ref.supabase.co
   SUPABASE_SECRET_KEY=sb_secret_xxxxxxxxxxxxxxxxxxxxxxxx
   ADMIN_PASSWORD=pick-a-real-password
   ```
6. `.env` is already in `.gitignore` — never commit it.

## Contact form email setup

The homepage's Contact section sends messages straight to the MLA's inbox using
SMTP (via Nodemailer) — no third-party form service needed.

**Easiest option: Gmail with an App Password**
1. Go to your Google Account → **Security** → turn on **2-Step Verification** (if not already on).
2. Go to **Security → App Passwords** → create one for "Mail".
3. Google gives you a 16-character password — use that (not your normal Gmail password).
4. In `.env`:
   ```
   SMTP_HOST=smtp.gmail.com
   SMTP_PORT=587
   SMTP_USER=your-gmail-address@gmail.com
   SMTP_PASS=the-16-character-app-password
   MLA_EMAIL=mlaoffice@example.com
   ```
   `MLA_EMAIL` is where messages get delivered — leave it out and it'll default to `SMTP_USER`.

Any other email provider works too (Outlook, Zoho, a custom domain inbox) — just
change `SMTP_HOST`/`SMTP_PORT` to match their SMTP settings.

Until SMTP is configured, the contact form will show a clear error instead of
silently failing — so you'll know right away if something's missing.

## Running it

```bash
cd mla-appointment-system
npm install
npm start
```

Then open:
- Citizen portal: **http://localhost:3000**
- Admin dashboard: **http://localhost:3000/admin.html**

### Admin password

Set in `.env` as `ADMIN_PASSWORD`. Default fallback is `changeme123` if not set —
change it before real use.

## How it works

1. A citizen fills the form on the home page → `POST /api/appointments` creates a
   record with `status: "pending"` and returns a token number like `MLA-000042`
   (auto-generated by a Postgres trigger).
2. The admin logs into `/admin.html` (password checked against `ADMIN_PASSWORD`) and
   sees all requests via `GET /api/appointments`.
3. For any pending (or previously rescheduled) request, the admin can:
   - **Approve** → confirms the citizen's preferred date/time as-is.
   - **Reject** → marks it rejected, no date is confirmed.
   - **Reschedule** → opens a small form to propose a new date/time + an optional
     note, and marks the status `rescheduled`.
   All three call `PATCH /api/appointments/:id`.
4. The citizen returns to the home page, enters their mobile number under
   "Check Request Status", and sees the current status, confirmed date/time (if
   any), and any note left by the office. This uses a Postgres function
   (`get_appointments_by_mobile`) so citizens can only ever see their own requests.
5. The Calendar tab on the dashboard shows every **approved/rescheduled** appointment
   plotted on its confirmed date, so the office can see availability at a glance
   before approving new requests.

## Things to harden before a real deployment

This was built to be simple to run and easy to extend, not production-hardened out of
the box. Before using it for real constituents, you'll want to:

- Replace the single shared admin password with full Supabase Auth (the SQL already
  has policies ready for `authenticated` users) — especially if more than one staff
  member needs access with logs of who approved what.
- Add SMS/WhatsApp notifications (e.g. via Twilio or an SMS gateway) so citizens are
  actively notified instead of having to check the status page themselves.
- Add double-booking protection (warn the admin if two approved appointments land in
  the same time slot).
- Add basic rate-limiting on `POST /api/appointments` to prevent spam submissions.
- Deploy behind HTTPS (Render, Railway, a VPS with Nginx, etc.) rather than running
  locally.

## Customizing

- Colors, fonts, and the "token slip" styling all live in `public/css/style.css` as
  CSS variables at the top of the file — change the header emblem text (`MLA`), the
  office name in the masthead, and the color palette there.
- Time slot rules (e.g. "only 10am–1pm, Mon–Fri") aren't enforced yet — add that
  validation in `server.js` inside the `POST /api/appointments` route if you want to
  restrict what citizens can request.
